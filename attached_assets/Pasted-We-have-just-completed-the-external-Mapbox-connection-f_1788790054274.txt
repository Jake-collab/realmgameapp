PHASE B — VERIFY MAPBOX CONNECTION

2. Required Mapbox token/config values are available through the intended environment-variable/configuration system.
3. Secrets are not hard-coded into source files.

PHASE D — LOCATION PERMISSIONS AND USER POSITION

Implement reliable user-location handling.

Requirements:

* Ask for location permission at the appropriate time.
* Do not repeatedly nag after denial.
* Handle:
    * granted
    * denied
    * permanently denied
    * location services disabled
    * temporarily unavailable location
* Display a clear user-location indicator when permission is available.
* Use a subtle animated/pulsing user-location marker if technically appropriate.
* Provide a recenter/current-location control.
* Do not treat client-reported location as authoritative for quest completion.
* Existing server-side verification remains authoritative.

Do not enable unnecessary continuous/background location collection simply because Mapbox supports it. Only collect the location needed for current gameplay/QAVS features.

PHASE E — DATA MODEL INTEGRATION

Map content must come from existing backend data rather than hard-coded demo markers.

Review existing location schemas and extend them only where necessary.

* availability
* active state

Hunt map data should be capable of representing:

* hunt_id
* objective/drop/location id
* coordinates when visible
* objective state
* visibility/reveal state
* point/reward data when appropriate
* current participant state
* completion state

Reuse existing schema whenever possible. Use proper migrations if schema changes are required.

PHASE F — PERFORMANCE AND MAP RELIABILITY

Ensure:

* Markers do not trigger unnecessary rerenders.
* Large marker collections are handled efficiently.
* Clustering may be used where appropriate for discovery-scale content, but never if it harms gameplay clarity.
* Map does not refetch everything on every minor camera movement.
* Navigation away from and back to a map does not unnecessarily reset important selected/active gameplay state.
* App relaunch can restore server-backed active Quest/Hunt state.
* Invalid/missing coordinates cannot crash the map.
* Duplicate coordinates are handled safely.
* Malformed backend data is skipped/logged rather than crashing the client.
