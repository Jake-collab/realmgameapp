REVEAL MODES

Support configurable objective reveal behavior such as:

ALWAYS_VISIBLE
Objective appears immediately.

PROXIMITY_REVEAL
Objective becomes visible when the player enters a configured reveal radius.

PREREQUISITE_REVEAL
Objective becomes visible only after specified previous objective(s) are completed.

HUNT_START_REVEAL
Objective becomes visible once the Hunt officially begins for that player.

ZONE_REVEAL
Objective becomes visible when a zone or area is unlocked.

CLUE_ONLY
Exact marker remains hidden while the player receives limited navigation information such as:

* approximate distance
* directional clue
* clue text
    depending on Hunt configuration.

MANUAL/ADMIN_REVEAL
Allow an authorized creator/admin-controlled state if the existing creator architecture supports it.

Do not expose hidden coordinates to the client before they should be known if doing so would defeat the reveal mechanic.

Where possible, the backend should only return precise hidden objective coordinates once the player satisfies the reveal condition.

FOG OF WAR

Implement optional fog-of-war/exploration visualization.

Requirements:

* enabled per Hunt
* does not obscure critical app controls
* performant on mobile
* discovered/explored areas can persist when the Hunt requires persistent exploration
* state is participant-specific
* cannot be trivially defeated by restarting the app
* backend stores the minimum state needed to reconstruct meaningful persistent exploration

Do not continuously store extremely granular location trails solely to draw fog-of-war if a less invasive zone/grid approach can achieve the same gameplay goal.

Choose a reasonable performant approach based on the existing architecture, such as:

* grid cells
* zones
* simplified explored polygons
* checkpoint-based reveal state

Avoid massive high-frequency coordinate tables.

HUNT ZONES

Allow Hunts to contain optional zones.

A zone may represent:

* neighborhood
* park
* building/public venue
* themed game region
* sequential stage

Support:

* locked
* available
* active
* completed

Zone progress may be derived from required objectives within that zone.

Example:

WATERFRONT ZONE
4 / 6 complete

When configured, completing a zone can unlock another zone.

OBJECTIVE DEPENDENCIES

Allow configurable prerequisite relationships.

Examples:

Objective B requires Objective A.

Objective D requires any 2 of A/B/C.

Zone 2 requires Zone 1 completion.

Be careful to prevent impossible dependency loops.

Add server-side validation preventing circular dependencies where appropriate.

AREA COMPLETION

Where a Hunt uses zones, allow a meaningful map statistic such as:

2 / 4 zones complete

or:

Downtown Zone
80%

Only calculate percentages where mathematically valid.

HIDDEN DATA SECURITY

Audit the API responses and client state.

A supposedly hidden objective should not simply have hidden UI while its exact latitude/longitude remains easily available in normal client data.

If current architecture sends every coordinate to the client, modify the data/API strategy so unrevealed precise coordinates can remain server-side until authorized for that participant.

Do not overengineer secrecy for casual gameplay, but avoid obvious client-side leaks.

Do not invent a completely separate safety platform. Extend the current moderation architecture so these capabilities can plug in later or use existing implementations if already present.
