# 1. Core Principle

Automation may:

- Approve clearly safe low-risk content when configured
- Flag questionable content
- Quarantine content
- Route to manual review
- Calculate integrity risk
- Prioritize moderation queues

Automation must NOT automatically:

- Permanently ban a user
- Permanently suspend a user
- Delete historical evidence
- Reverse major point balances without trusted policy
- Reject ambiguous safety-sensitive cases without review
- Expose moderation internals to ordinary users

High-impact enforcement must remain reviewable.

---

# 2. Moderation Provider Abstraction

Create a provider abstraction such as:

```ts
interface ModerationProvider {
  moderateImage(...)
  moderateText(...)
  healthCheck(...)
}
````

Support:

* Current provider
* Future provider replacement
* Development stub
* Manual-only mode

Do not tightly couple moderation logic to one vendor.

Do not place provider secrets in the client.

# 3. Server-Side Moderation Only

All moderation-provider calls must occur server-side.

Allowed architecture:

```text
Upload or content submission
    ↓
Trusted backend / Edge Function
    ↓
Moderation provider
    ↓
Normalized result
    ↓
Platform moderation policy
    ↓
Approve / Flag / Quarantine / Manual Review
```

Do not call the moderation provider directly from Expo or browser client code.

* Safe content

* Moderation-warning content
* Yet still relevant to the Quest

Keep these decisions separate.

* Safe
* Warning

* Blocked

* Proof validity = Rejected
