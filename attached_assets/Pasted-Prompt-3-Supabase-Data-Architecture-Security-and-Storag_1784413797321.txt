# Primary Objective
Design and implement a scalable Supabase data architecture for Worlds that supports:
- User accounts and profiles
- Onboarding
- Quest
- Geo-Quests
- Hunt
- Custom Games
- Invitations
- Progress and completion
- Proof submissions
- Points
- Achievements
- Leaderboards
- Notifications
- Reports
- Moderation
- Admin operations
- Media storage
- Future AI-generated content
- Future social and monetization extensions without requiring a major rewrite
The schema must be normalized, secure, understandable, and practical.
Avoid unnecessary complexity.
Do not create separate duplicate systems for Quest and Hunt when a shared system is appropriate.

3. Database Extensions and Conventions

Use UUID primary keys.

Use created_at and updated_at timestamps consistently.

Use UTC timestamps.

Use database-generated timestamps where practical.

Use soft deletion or archival states where deleting records would damage history.

Use restrictive foreign-key deletion behavior for financial, moderation, completion, points, and audit records.

Enable appropriate PostgreSQL extensions where useful, such as:

* pgcrypto
* PostGIS only if justified for geospatial storage and queries

Do not add extensions without a clear purpose.

Use snake_case database naming.

Use TypeScript-friendly enums or constrained status fields.

Add comments to important tables and columns where they improve maintainability.

34. Row Level Security

Enable RLS on all exposed application tables.

Create explicit policies.

Do not rely on the absence of UI controls for security.

At minimum, enforce:

Profiles

* Public access only to approved safe profile fields through a view or controlled query.
* Users update only their own allowed profile fields.
* Users cannot update role or account status.

User settings

* Owner-only access.
* Admin access only where operationally necessary.

Quests

* Public users read only published, active, nonrestricted Quest records.
* Drafts are visible only to authorized staff.
* Users cannot create or publish official Quests.

Quest participation

* Users access only their own participation.
* Trusted server logic handles protected completion and point-award fields.

Proof

* Owner and authorized reviewers only.

Hunts

* Public Hunts may be visible appropriately.
* Private and invite-only Hunts require membership or invitation.
* Custom Game creators may manage only their own allowed records.
* Official Hunt publishing requires admin authority.

Invitations

* Only inviter, invitee, Hunt creator where appropriate, and staff.

Points

* Users can read their own ledger.
* Users cannot insert, update, or delete point records.

Reports

* Reporters can create reports.
* Reporters may access only their own report status where appropriate.
* Reported users cannot access reporter identity.

Notifications

* Owner-only read and update.
* System-created only.

Audit logs

* No ordinary user access.
* Authorized staff read-only.
* Trusted backend inserts.

Test all policies with representative roles.
