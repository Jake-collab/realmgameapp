# 2. Core Architecture

Notifications must use one canonical notification pipeline.

Use architecture conceptually equivalent to:

```text
Domain Event
    ↓
Notification Policy
    ↓
Notification Record
    ↓
Delivery Queue
    ↓
In-App Delivery
    +
Push Delivery
    ↓
Delivery Status
```

Do not scatter direct push-provider calls throughout Quest/Hunt code.

Gameplay services should emit trusted events.

The notification layer determines delivery.

---

# 3. Notification Is Not the Source of Truth

Never use notification delivery as authoritative gameplay state.

Example:

If a Quest proof is approved:

1. Trusted completion transaction occurs.
2. Points are awarded.
3. Domain event is created.
4. Notification is generated.

Do NOT:

1. Send notification.
2. Assume notification means completion succeeded.

The database remains authoritative.

# 4. Notification Provider Abstraction

Create a push provider abstraction.

Example:

```ts
interface PushNotificationProvider {
  send(...)
  sendBatch(...)
  validateToken(...)
  healthCheck(...)
}
```

Support the current Expo/React Native architecture.

If Expo Push Notifications is appropriate for the existing project, integrate it behind the abstraction.

Do not tightly couple all domain code to Expo.

Future native APNs/FCM migration should be possible.

---

# 5. Server-Side Delivery

Push notifications must be initiated by trusted backend infrastructure.

Do not allow clients to send arbitrary push notifications to other users.

Architecture:

```text
Trusted Event
   ↓
Notification Worker
   ↓
Push Provider
   ↓
Registered Device
```

Client may register its own push token.

Client may not select arbitrary recipients and message payloads.

Create/verify a device registration model.

* Push token
* Platform
* App version
* Device metadata only where operationally necessary
* Created at

* Enabled

One user may have multiple devices.

One device token must not remain incorrectly attached to an old account after logout/account switching.

# 7. Token Lifecycle

Implement:

## Login

Register/associate current installation.

## Token refresh

Update token.

## Logout

Detach or disable association safely.

## Invalid token

## Reinstall

Allow new installation/token.

Do not continuously create duplicate device rows.

# 14. Push Tap Behavior

When user taps push:

1. Open Worlds.
2. Resolve authenticated state.
3. Resolve notification target.
4. Verify user can access target.
5. Navigate to correct screen.

If target no longer exists:

Show safe fallback rather than broken route.

Example:

**This activity is no longer available.**

---

# 15. Logged-Out Deep Links

If push is tapped while logged out:

1. Preserve safe intended destination locally.
2. Show login.
3. After successful authentication, revalidate destination.
4. Navigate if authorized.

Do not bypass authentication.

# 96. RLS

Ordinary user:

* Read own notifications
* Update own read/archive state
* Read/update own preferences
* Register own device through trusted operation

Cannot:

* Create arbitrary notification for another user
* Read another user's notifications
* Read raw delivery diagnostics
* Read another user's push token

Admin:

Permission-scoped operational access.

Push tokens must be protected.
