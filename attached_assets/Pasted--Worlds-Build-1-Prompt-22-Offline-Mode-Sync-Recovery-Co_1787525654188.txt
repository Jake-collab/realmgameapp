# Primary Objective

Make Worlds resilient to:

* No internet
* Weak cellular service
* Temporary Supabase outages
* Temporary Mapbox outages
* Upload interruptions
* App termination
* Device restart
* Network switching
* Duplicate mutation attempts
* Lost server responses
* Background/foreground transitions
* Multi-device conflicts
* Stale cache
* Partial sync
* User logout during pending work

while preserving strict server authority for:

* Quest completion
* Hunt completion
* Points
* Proof submission
* Location validation
* Friend/social actions
* Hunt invitations
* Moderation
* Admin actions
* Publication
* AI generation

Offline functionality must never create fake authoritative success.

---

# 1. Core Offline Principle

Use this rule everywhere:

```text
Offline may preserve intent and evidence.

Offline may NOT fabricate server confirmation.
```

For example:

Allowed offline:

* Read previously cached Quest information
* Read previously authorized Hunt clue
* Draft text proof
* Capture proof image
* Edit creator Hunt draft locally
* Browse previously loaded map data
* Mark in-app notification read locally for later sync
* Queue safe non-authoritative actions where approved

Not allowed offline:

* Award points
* Approve proof
* Validate protected location
* Complete Quest authoritatively
* Complete Hunt authoritatively
* Accept Hunt invitation as confirmed
* Join a full Hunt as confirmed
* Change leaderboard rank
* Publish Hunt
* Moderate content
* Generate AI content and claim it succeeded

# 2. Offline Architecture

Create one shared synchronization layer.

Suggested structure:

```text
/features/offline/
  storage/
  queue/
  sync/
  conflicts/
  connectivity/
  recovery/
  hooks/
  services/
  types/
  tests/
```

Responsibilities:

## Local Storage

Persists safe offline state.

## Mutation Queue

Queues approved retryable actions.

## Sync Engine

Processes queued work after connectivity returns.

## Conflict Resolver

Handles stale local state versus newer server state.

## Connectivity Service

Tracks useful network status.

## Recovery

Restores interrupted work after restart.

Do not create separate offline systems for Quest, Hunt, Notifications, and Creator flows.

# 12. Queue Eligibility

Not every mutation should be queued.

Categorize mutations:

## Safe to queue automatically

Examples:

* Notification read state
* Creator draft edits
* Profile preference edits where conflict rules are defined
* Non-authoritative text draft sync
* Local media upload intent

## Queue only after explicit user action

Examples:

* Proof submission intent after user presses Submit
* Creator draft save

## Must require live server connection

Examples:

* Join Hunt
* Accept invitation
* Start Hunt requiring availability
* Location validation
* Quest completion
* Hunt completion
* Point-related action
* Moderation action
* Admin role change
* Hunt publication
* AI generation

Do not blindly queue every failed API mutation.

---

# 13. Idempotency

All queued mutations must use deterministic idempotency.

Examples:

```text
proof_submission:{localSubmissionId}
creator_draft_save:{draftId}:{localVersion}
notification_read:{notificationId}
proof_media_upload:{localAssetId}
```

When retry occurs:

* Server must return existing successful result when possible
* Do not duplicate submission
* Do not duplicate upload record
* Do not duplicate notification action

This is critical.

# 15. Queue Ordering

Process queued operations based on:

1. Required dependencies
2. Entity order
3. User action priority
4. Creation time

Do not let a later draft save overwrite a newer local draft through old queue ordering.

Collapse superseded update operations where safe.

# 16. Superseded Draft Mutations

For rapidly edited drafts:

Example:

```text
Update title A
Update title B
Update title C
```

If none were sent:

Collapse to latest safe draft state.

Do not waste network calls.

Do not collapse immutable actions such as proof submission.

# 17. Sync Engine

When connectivity returns:

1. Revalidate authenticated session.
2. Verify current user matches queue owner.
3. Refresh critical server state.
4. Process dependencies.
5. Process safe queued mutations.
6. Handle conflicts.
7. Update local state.
8. Refresh affected React Query keys.
9. Remove completed queue items after retention window.

Do not immediately blast every queued operation concurrently.

Use bounded concurrency.
